# NestJS Base Project

## Опис проєкту

Цей проєкт є базовою заготовкою NestJS-застосунку, створеною з метою
правильної ініціалізації, формування початкової архітектури та фіксації
архітектурних рішень.

Основний фокус зроблено на **структурі проєкту,
модульності та підготовці основи для подальшого масштабування**.

---

## Технологічний стек

- **Node.js (LTS)**
- **NestJS**
- **TypeScript**
- **@nestjs/config** для роботи з environment variables

---

## Загальна архітектура

NestJS з самого початку задає архітектурний напрямок:
модульність, dependency injection та розділення відповідальностей.

У цьому проєкті використовується **модульна та шарова архітектура**, де:

- точка входу в застосунок є мінімальною;
- бізнес-функціональність ізольована в окремих модулях;
- конфігурація винесена в окремий інфраструктурний шар;
- всі модулі збираються в одному кореневому місці.

---

## Структура проєкту

```bash
src/
├── app.module.ts
├── main.ts
├── config/
│   └── app.config.ts
├── modules/
│   └── users/
│       ├── users.module.ts
│       ├── users.controller.ts
│       └── users.service.ts
└── common/
```

### Пояснення структури

- **`main.ts`** — точка входу, відповідає лише за bootstrap застосунку.
- **`AppModule`** — кореневий модуль (composition root), який збирає всі модулі та інфраструктуру.
- **`modules/`** — бізнес-модулі, кожен з яких інкапсулює свою логіку.
- **`config/`** — централізована конфігурація середовища.
- **`common/`** — місце для спільних рішень (guards, pipes, utils), наразі порожнє.

---

## UsersModule

`UsersModule` створений як приклад feature-модуля.

Він демонструє:

- розділення транспортного рівня (`Controller`);
- бізнес-логіки (`Service`);
- інкапсуляцію залежностей всередині модуля.

---

## Конфігурація середовища

Для роботи з environment variables використовується `@nestjs/config`.

- конфігурація підключена глобально;
- всі змінні централізовано описані в `app.config.ts`;
- файл `.env.example` використовується як шаблон.

Змінна `NODE_ENV` використовується як стандартний індикатор середовища та може
бути розширена в майбутньому для environment-based конфігурації.

---

## Звʼязок з DDD

Проєкт **не реалізує повноцінний Domain-Driven Design**, оскільки:

- відсутній сформований домен;
- немає складних бізнес-правил.

Водночас поточна структура **не суперечить DDD** і дозволяє еволюційний перехід до нього:

- feature-модулі можуть стати bounded contexts;
- логіку можна розділити на domain / application / infrastructure шари.

Таким чином, обраний підхід є свідомо спрощеним, але архітектурно підготовленим.

## Запуск застосунку

1. Встановити залежності:

```bash
  npm install
```

2. Перейменувати **`.env.example` → `.env`** і заповнити значеннями

3. Запустити проект у дев режимі

```bash
  npm run start:dev
```

## homework5

**Транзакція.** Створення замовлення виконується в одній транзакції через TypeORM QueryRunner. Підключення до БД береться через DataSource.createQueryRunner(), стартується транзакція startTransaction(), вся логіка (блокування продуктів, перевірка залишків, створення замовлення та позицій) виконується в її межах, потім транзакція комітиться або відкочується при помилці. QueryRunner звільняється в блоці finally

**Механізм конкурентності.** Використовується песимістичне блокування pessimistic_write. Під час створення замовлення продукти зчитуються з блокуванням FOR UPDATE, щоб уникнути race condition при одночасному оновленні залишків

**Ідемпотентність.** У сутності Order є унікальне поле idempotencyKey. Перед транзакцією перевіряється наявність замовлення з таким ключем; якщо є - повертається існуючий результат. Ключ можна передати через заголовок Idempotency-Key або в тілі запиту. При помилці unique violation (код 23505) через паралельні запити з однаковим ключем система також шукає існуюче замовлення за idempotencyKey і повертає його замість падіння

**Оптимізація запитів та індекси.** Оптимізовано запити, пов’язані з продуктами та позиціями замовлень. Додано індекси: idx_products_name для пошуку та сортування продуктів за name; idx_order_items_product_id та idx_order_items_order_id для швидких JOIN і фільтрації по order_id та product_id при завантаженні замовлень з позиціями
